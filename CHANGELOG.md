## [0.8.0]

FEATURES:

* `sreagent_github_account` manages the settings of one GitHub account the organization connected: open fix pull requests automatically (`auto_pr_enabled`), revise a pull request when a review asks (`auto_revise_on_review`), open them as drafts (`draft_prs`), review pull requests (`review_enabled`), comment links on linked issues (`link_comments_enabled`), "Auto-merge only what SRE Agent verified" (`auto_merge_requires_verification`) and the lowest severity a review comments on (`review_severity_floor`). It is the per-account form of `sreagent_github_settings`, which keeps the organization's managed account (the one connected longest) and the context repository: use `sreagent_github_account` for the organization's other accounts, because a block for the managed account writes the row `sreagent_github_settings` writes, and the plan warns when the account a block adopts is the managed one. `account_id`, `account_type`, `installation_id`, `status`, `managed`, `holds_context_repo`, `repository_count`, `repos_truncated`, `repos_refreshed_at` and `repos` (at most 500 repositories, as JSON) are read from the platform. `data.sreagent_github_accounts` lists every connected account.
* `sreagent_github_child_access` manages what a parent organization gives one child organization of one of the parent's GitHub accounts: `mode` (`all`, `selected` or `none`), `repositories` (the repositories of a `selected` child, at most 500, `owner/name`) and `context_repo_shared` (whether the child may use the parent's context repository). One block for each child and account, in the parent organization. A change that takes repositories away from the child is applied only against a preview of what it moves: `terraform plan` asks the platform for the preview (it writes nothing, and needs an `api:admin` key; with a plan-only `api:config_read` key the plan says so, and the apply previews and applies) and warns with what the child may use now and will use, the repositories it stops reaching, and what is held on them (open fix pull requests stay open on GitHub with one comment saying SRE Agent no longer manages them, auto-merge is turned off, and waiting requests and cards are named; nothing is closed or deleted). The apply sends the plan's fingerprint, and fails without writing when what would move changed since the plan (plan again). A change that takes nothing away, such as giving the child more or changing only `context_repo_shared`, is applied at once. The plan refuses `repositories` with any mode but `selected`, a `selected` child with none, and a repository the account does not reach. A repository is the same in any case (`acme/web` and `Acme/Web`; naming both is refused), and state keeps the spelling the block wrote. A block that names the child by its name where it was imported by its id (or the login in another case) is not a new row: the plan shows one in-place update that sends nothing, never a replacement. `data.sreagent_github_child_access` lists every row of the parent.
* `data.sreagent_ticket_templates`, `data.sreagent_ticket_schedules`, `data.sreagent_board_rules` and `data.sreagent_lead_agent_settings` read the board's card templates, its recurring cards, its rules and what SRE Agent does with work it is given (card, Slack and alert modes, plan approval, its limits and, for alerts, paging, acting without a person, the lowest severity and the hourly start limit). They are read only: the platform publishes no Terraform type for them, and each is written in the app (or over MCP). `trigger`, `conditions`, `actions`, `weekdays`, `last_run`, `bounds` and `modes` are JSON.
* `data.sreagent_effective_repo_settings` answers `account` for each repository: the GitHub account it is read through, or null when no account lists it.
* The provider now declares every field the platform had published ahead of it: `card_event_kinds` (the whole set of card event groups a webhook target receives, from `approvals`, `created`, `moved`, `assignees`, `comments`, `checklist`, `relations` and `closed`; the platform's default is `approvals` alone) and `card_event_text` (whether those events carry comment bodies, checklist text and a won't-do reason, off by default) on `sreagent_outbound_config`; `good_events_query`, `total_events_query`, `threshold_good` and `unit` on `sreagent_sli`; and `board_summary_model_enabled` (whether the weekly board summary is also written by a model, from the organization's own AI provider only, off by default) on `sreagent_organization_settings`. Each is sent only when the configuration states it, and a value the configuration leaves out is left as it is.
* The vendored API document is re-vendored whole, which ends the daily contract drift failure that named the four data sources, `account` and the fields above as missing from the provider. The two new resources are the exception: the drift check names them until the platform release that publishes them as Terraform types is deployed, and the failure ends once it is. The contract test now also holds a row addressed by a path value and a query value (`github_child_access`), a previewed collection row and the child access preview (the 428 and 409 of its update), and checks that the document agrees with the provider once the platform empties its lists of what a release declares.

## [0.7.0]

FEATURES:

It is a map from a column (`backlog`, `triage`, `todo`, `in_progress`, `blocked` or `done`) to one emoji written as the emoji itself. A column left out has no emoji, `{}` removes them all, and the map replaces what the organization holds, so a column the platform has an emoji for and the configuration leaves out is removed. The setting is display only: it changes what the board's column headers, the Move to menu, the card's status buttons and the new card form say. An organization admin's key (`api:admin`) may change it. The data source answers it too.
* `sreagent_organization_settings` takes `slack_reaction_sync` (`both`, the platform's default, `from_slack` or `off`): how reactions travel between a card and its Slack threads. `from_slack` shows a reaction made in Slack on the card and makes SRE Agent add none in Slack; `off` stops both. Switching never removes reactions already in place. An organization admin's key (`api:admin`) may change it. The data source answers it too.
* `sreagent_organization_settings` takes `slack_reaction_counts` (on by default): whether SRE Agent's messages in a card's Slack thread carry the board's counts. An organization admin's key (`api:admin`) may change it. The data source answers it too.
* `data.sreagent_alert_follow_up_settings` reads the three switches an organization admin turns on in Settings: `telemetry_checks_enabled` (judging alerts SRE Agent cannot ask directly: Datadog monitors, New Relic issues, silence and the alert's own condition), `telemetry_model_enabled` (the organization's own AI provider works out a check, as a hint only; it needs the first) and `informative_learning_enabled` (a daily suggestion of the kinds of alert that look informative). Each is off until an admin switches it on. It is still a data source only: the platform publishes no Terraform type for the follow-up.
* The vendored API document is re-vendored whole, which keeps the daily contract drift job green. The contract test now also holds a map attribute to its write body (the columns it names, the length of each value) and checks that the document agrees with the provider once the platform empties its lists of what a release declares.

## [0.4.0]

FEATURES:

* `sreagent_repo_setting` and `sreagent_repository_defaults` take `auto_merge`, the seventh repository setting: whether a fix pull request merges by itself once the checks its branch requires pass. SRE Agent asks GitHub to merge it when the checks are still running and merges it itself when they have already passed, only where the repository allows auto-merge and the base branch requires a status check; a draft, a change its own checks could not judge, CI, IAM and Kubernetes manifest changes, and a self-healing pull request below full autonomy never merge this way. It is off unless set. Your organization's admins take the risk of a merge nobody reviewed, and the attribute's description says so. On a row it behaves like `check_network` and `allow_ci_config`: left out it is left as it is, stated with the value the row already reads it is not written, and `follows_default` may name it (the plan warns that the apply puts it back on the default). `follows_default` and `following` count seven settings now.
* Turning auto-merge on needs the platform's confirmation. `sreagent_repo_setting` gains the write-only `confirm` (the only value is `auto_merge`); `sreagent_repository_defaults` takes `auto_merge` in its existing `confirm`, and in `confirm_on_destroy`. The plan fails without it, with the platform's sentence and the line to add: a write that sets `auto_merge = true` on a row that does not already read it on, a create included, and a defaults change that turns it on. What the plan cannot see (a reset with `follows_default` onto a default that says on, an all-branches entry that branch entries follow, removing an all-branches entry that says off under a default that says on) is refused by the platform at apply, and the refusal is shown with its own sentence. A `confirm` the write does not need is harmless, and naming it never writes anything by itself. It is not stored: remove it after the apply that turned the setting on, because a confirmation left in the configuration also confirms every later apply that turns auto-merge on again, including one that undoes a person turning it off in the app. The same holds the other way: a configuration that states `auto_merge = true` without `confirm` fails the plan again whenever the platform stops reading it on (a person turned it off in the app, or a default the row followed was turned off); add `confirm = ["auto_merge"]` for the apply that turns it on again, or set `auto_merge = false` (or remove the line) to leave it off. The preview a defaults plan warns with now names the repositories whose pull requests would start and stop merging by themselves, and those that open as drafts and never do.
* `sreagent_github_settings` takes `auto_merge_requires_verification` ("Auto-merge only what SRE Agent verified"): off by default, a fix SRE Agent's own checks did not run for can still merge by itself once the checks its branch requires pass; on, only a fix whose exact commit those checks ran on and passed does. A fix whose checks failed, or ran and could not judge it, never merges by itself in either position.
* `sreagent_organization_settings` takes `language` (`en` or `es`, the language of the outcome lines SRE Agent writes into a card's Slack threads), `slack_thread_events_off` and `reaction_quick_row`. `slack_thread_events_off` is the whole set of events not posted in those threads, from `column_moves`, `card_done`, `card_wont_do`, `pull_request_opened`, `pull_request_merged`, `pull_request_closed`, `pull_request_reopened`, `change_pushed`, `assistant_replies` and `comments`; `[]` posts everything, the order does not matter (the platform stores it sorted), and a failed or declined fix or change is always posted and has no name. `reaction_quick_row` is the emoji shown first when someone adds a reaction, in order, as the whole list: at most 12, each one emoji of at most 16 code points, `[]` for SRE Agent's twelve. An org admin's key (`api:admin`) may change all three.
* An emoji in `reaction_quick_row` round-trips without drift. The platform stores the fully qualified form of each emoji (a heart written as one code point comes back with its presentation selector), so the provider treats two spellings that differ only by U+FE0E or U+FE0F as the same value: your spelling stays in state and plans no change, importing the platform's spelling plans nothing for a configuration that writes the bare one, and a ZWJ sequence, a skin tone and a flag with a selector inside are sent exactly as written. The order is part of the value. The plan refuses what it can judge, so a bad value does not plan a change on every run: a Slack name such as `:tada:` (the platform accepts it and stores the emoji it names, which would read back as a different value), the same emoji twice in any spelling, more than 12 entries, and an entry over 16 code points (the platform's bound for one emoji, `SreData.Emoji.normalize/1`: at most 16 code points and 64 bytes; the published `items.maxLength` of 64 is the looser one). Whether a value is an emoji of the platform's set only the platform knows, and its refusal is shown as a diagnostic.
* `data.sreagent_alert_follow_up_settings` reads the alert follow-up setting: whether SRE Agent checks alerts that stay open, what it does with one its source says has cleared (`resolve_modes`), the ages at which it checks, reminds, opens a card and escalates (`ages`), the kinds that are only being suggested (`demoted`), and what it did in the last 7 days (`week`). `data.sreagent_alert_informative_kinds` lists the kinds of alert marked expected (`status` filters one status or `all`; the default is proposals and approved kinds), with `counts` and `limits`. Both are read only. The platform publishes no Terraform type for them: an organization admin switches the follow-up on and decides a kind in the app, and it is off until then, so a resource would only fight that decision. They become resources when the platform types them.
* The vendored API document is re-vendored whole, which ends the daily contract drift failure that named `auto_merge`, the `confirm` and `follows_default` enums, `auto_merge_requires_verification`, the three organization settings and the two alert follow-up views as missing from the provider. The contract test now also holds an unpaged list data source's query arguments (and their enums) and extra keys to its GET, and a list entry's `maxLength` to the published `items.maxLength`.

Destroying the resource leaves the settings in place and says that the digest keeps sending while it is on; to go back to the defaults (`enabled = false`, `cadence = "weekly"`, `weekday = 1`, `hour = 9`, `slack_channel = ""`, `email = false`), state them, apply, then remove the block. Import with the id `security_digest_settings`.
* `sreagent_security_code_classes` manages the `other:<kind>` classes counted as security findings, beyond the four built-in classes. `classes` is the complete list: a class left out is unmarked and `[]` unmarks them all. It is a set (at most 50), so the order does not matter and the platform's sorted answer plans nothing. The plan fails for a built-in class, which always counts, and for a class the organization has not accepted (`available_classes` lists the ones it can mark), and it warns for each class it unmarks that its open findings close and that marking it again restores them. Destroying the resource leaves the marks in place and says so. Import with the id `security_code_classes`.
* `sreagent_security_notification_rule` manages a security notification rule: `name` (required, 1 to 80 characters), `enabled`, `areas` (empty means every area), `min_severity`, `events` (at least one), `slack`, `slack_channel`, `email` and `page`. Unlike the three settings above, an attribute the configuration leaves out takes the platform's default (on, every area, minimum severity `high`, the `new_finding` event, Slack and email on, paging off), so removing `page = true` stops paging; `slack_channel` left out, or removed, sends null for the default channels. The plan fails for paging on a rule whose `min_severity` is not `critical` and for a rule with no destination (Slack, email and paging all off), and checks the areas, severities, events and channel against the platform's lists and limits. An organization has at most 20 rules and a name is unique: the platform refuses the 21st rule and a duplicate name at apply with its own sentence, and a duplicate says to import the existing rule. Destroying a rule deletes it; the rule the platform seeds, Critical and high findings, is imported to be managed (its events are `new_finding`, `sla_breached`, `acceptance_expired` and `fix_verified`, so a block that leaves `events` out plans a change to `new_finding`), and once every rule is deleted the platform sends no security notice and never creates the seeded one again. Import with the rule's id.
* `sreagent_secret_allow_rule` manages a rule that keeps the weekly repository scan from filing a credential match, by `path_glob` and `reason` (both required, trimmed) and optionally `repository` (`owner/name`), `detector_type` and `expires_at` (a time with a zone). The platform has no update door, so any change replaces the rule, deleting the old one first; set `lifecycle { create_before_destroy = true }` to avoid the gap, up to the 100 rule limit. Removing `repository`, `detector_type` or `expires_at` replaces the rule with one that covers every repository, every kind, or never ends, and the plan warns what widens. The repository is stored in lower case and the end time with microseconds; neither is a change. A new rule that ends in the past fails the plan, and so does editing any field of a rule whose end has passed (the replacement would end in the past, and the old rule would be deleted first): the plan names the end and says to set a later `expires_at` or remove the block. A rule whose end has passed and is left as it is warns that it covers nothing and plans nothing else. A rule holds no credential, and the platform refuses a reason that looks like one. Import with the rule's id.
* All five need the infrastructure suite in the organization's plan, besides the configuration API. When it is missing the platform answers 403 to every read and write, and the plan fails with `Could not read sreagent_<type>`, the platform's sentence and the ways to stop managing the resource (`terraform state rm`, or a `removed` block whose `lifecycle` sets `destroy = false`, on Terraform 1.12 or later); a create refused this way has nothing in state, so it says to remove the block. The provider never reads that answer as a deleted row. An `api:config_read` key plans them and the platform refuses the apply, as for every resource.
* A block for a security setting that is not imported adopts what the organization already has, and the apply overwrites what the block names. Terraform shows that as a plain create, so for the three settings the plan reads the current settings (a read, never a write) and warns what the apply will change: each class it unmarks and that its open findings close, each SLA day that moves and that due dates are recomputed, and every attribute whose value differs, from the current value to the new one. The checks that need the current values run on a create too: a class the organization has not accepted, a built-in class, and a digest that would be on with no Slack channel and no email (counting the destination the organization already has) fail the plan before anything is written. When the plan cannot read the settings (a 403, or an answer it cannot parse) it warns and goes on, and a 404 from a platform that predates the setting says which release serves it. Import first to review the change as an ordinary plan.
* The plan-time limits of the five are the platform's own, published in its API document (day ranges, length bounds counted in characters, patterns, lists, defaults and the values that stand for null), and the contract test holds each of them to that document, so a limit the platform changes fails the daily drift check instead of drifting.
* The vendored API document is re-vendored whole.
